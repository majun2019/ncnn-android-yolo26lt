# Electronics 取向改稿清单

本文当前稿件若确认转投 Electronics，整体可行性高于继续按 Sensors 的实验型路线推进。原因在于，现有稿件最强的部分并不是算法创新或横向 benchmark，而是 Android 端统一部署、JNI/NCNN 协同设计、部署一致性问题定位、故障模式抽象与设备端验证。因此，改稿的核心不是继续把文章包装成“检测模型论文”，而是把它重构为一篇“资源受限移动设备上的多任务视觉推理部署与诊断系统论文”。

下面按优先级给出 Electronics 取向改稿清单。

## A. 必须先修：先把稿件从“模型稿”改成“系统稿”

### A1. 重新定义全文研究问题

- 将研究问题从“YOLO26 在 Android 上是否能运行”改写为“资源受限 Android 设备上多任务视觉推理系统如何实现统一部署、稳定解析与一致性恢复”。
- 将“YOLO26”持续定义为本文工程上统一管理的一组模型资产，而不是一个新提出的通用模型家族。
- 在引言前半部分保留边缘视觉背景，但在引言后半部分明确：本文研究重点是部署一致性与系统实现，而不是新的检测器结构设计。
- 把 SafeHat 检测案例定位为“完整闭环验证主案例”，而不是全文唯一的算法贡献来源。

**完成标准**：审稿人读完标题、摘要和引言后，会把本文理解为移动端视觉部署系统论文，而不是实验不完整的算法论文。

### A2. 重写标题、摘要与贡献点

- 标题弱化 YOLO26 和单一检测指标，强化 Android、NCNN、统一部署、诊断与验证。
- 摘要按“问题背景 - 系统方法 - 案例与验证 - 关键结果 - 系统意义”重写，不再把 mAP50 放在最显眼位置。
- 贡献点改成系统论文语言，不再写成“实现了五类任务”这种模块罗列式表达。
- 将“部署故障分析”上升为“部署一致性诊断方法”，明确其可迁移性边界。

**可选标题方向**：
- 面向 Android 设备的基于 NCNN 的多任务视觉推理统一部署与一致性诊断框架
- 资源受限移动设备上的多任务视觉推理部署与故障诊断方法
- 基于 JNI/NCNN 协同的 Android 多任务视觉推理部署与一致性验证框架

**建议贡献改写方向**：
- 提出一种面向 Android 端多任务视觉推理的统一部署架构，实现 Java、JNI 与 NCNN 原生推理链路的协同调度。
- 总结一套面向模型转换与设备端解析偏差的部署一致性诊断流程，可定位预处理、激活、坐标语义与输出布局等典型故障。
- 通过 SafeHat 主案例与五类任务设备端运行覆盖，验证该框架在资源受限移动设备上的可用性、可诊断性与功能完整性。

**完成标准**：摘要、引言贡献点、结论三处表述语义一致，并且都围绕“系统部署与一致性诊断”展开。

### A3. 清理仍偏“算法稿”的表达

- 弱化“验证集 mAP50 达 0.796”在全文中的主导地位，将其改成主案例训练质量说明，而不是全文主结论。
- 不再暗示“五个任务都完成了同等强度的定量验证”，而应明确为“一个主案例 + 五任务设备端功能覆盖”。
- 避免把图 8(c) 的五任务运行证据写成等价于五任务完整 benchmark。
- 不再使用容易引导算法审稿预期的措辞，如“新的视觉推理框架优于已有方法”“多任务统一提升精度”等。

**完成标准**：全文不会再让审稿人自然期待跨模型、跨框架、跨设备的大规模精度对比。

### A4. 修正正文中的硬性不一致问题

- 修正分类任务输入尺寸不一致问题：表 2 中写为 224×224 resize，而表 10 分类延迟备注仍写成 640×640 letterbox，必须统一。
- 统一“CPU / GPU / Turnip / Vulkan”四类术语的层级关系，避免同时用后端类型和具体图形接口混写。
- 统一“部署闭环”“真机验证”“运行覆盖”“功能验证”“一致性恢复”等结果表述，不要在不同段落切换口径。
- 统一“E2E / One-to-Many / Legacy”在全文的大小写、连字符与首次定义方式。

**完成标准**：任一系统设定、输入口径、任务语义或结果结论，在全文只能有一套说法。

## B. 重点增强：把稿件改成更像 Electronics 的系统论文

### B1. 强化“为什么这是 Electronics 关心的问题”

- 在引言中明确指出：本文不是一般算法部署记录，而是资源受限移动设备上的视觉系统协同设计问题。
- 把研究场景落到 Electronics 更熟悉的话语体系：嵌入式推理、移动计算、边缘 AI、系统集成、实时资源约束。
- 强调 JNI/NCNN 桥接、任务统一调度、设备端故障诊断与运行稳定性，这些属于系统实现与电子设备应用问题。
- 将 SafeHat 的工业安全场景作为应用支撑，而不是将论文定位成纯行业应用论文。

**完成标准**：审稿人会把本文归到 embedded/mobile AI systems，而不是 solely computer vision accuracy paper。

### B2. 重写第 2 节相关工作边界

- 将相关工作从“YOLO / E2E 检测器背景”扩展为三组：
	- 移动端与边缘端视觉推理框架
	- Android / embedded 设备上的神经网络部署与系统协同
	- 模型转换、一致性验证与设备端故障诊断
- 减少对通用检测模型发展史的篇幅投入，不再让相关工作过度像 detection survey。
- 增加对 TensorFlow Lite、MNN、ONNX Runtime Mobile、NCNN 的系统性对照描述，但不必新增实验比较。
- 引出本文位置：不是提出新框架替代所有移动推理引擎，而是围绕 NCNN 构建一个统一部署与诊断工作流。

**完成标准**：第 2 节能自然导向“为什么第 3、4 节的系统与诊断才是本文主贡献”。

### B3. 把第 3 节扩成全文第一主线

- 将第 3 节标题从“部署框架”进一步强化为“系统架构与统一部署流程”。
- 在第 3 节开头明确系统目标：统一任务调度、统一预处理、统一模型加载入口、统一设备端可观测性。
- 对 Java 层、JNI 层、C++ 层、NCNN 执行层的职责边界进行更结构化描述。
- 增加一段专门说明：为何采用 JNI/NCNN 组合，而不是将部署逻辑停留在更高层封装中。
- 将表 2、表 3、图 2、图 3 的逻辑关系重排为“系统组件 - 任务调度 - 部署流程”三层叙述。

**完成标准**：第 3 节本身就能独立支撑“这是一篇系统实现论文”的判断。

### B4. 把第 4 节明确为全文第二主线

- 明确第 4 节不是杂项 bugfix 汇总，而是“部署一致性诊断方法与典型故障模式”。
- 在节首给出一句总括：本文贡献不仅在于系统可以运行，还在于系统能够对部署偏差进行结构化定位与修复。
- 将四类故障统一写成“现象 - 根因 - 定位方法 - 修复动作 - 修复后状态”的标准模板。
- 把 S1-S5 诊断流程写成方法框架，而不是案例后验总结。
- 适当强调该流程对类似 Android 端模型转换与解析问题的参考价值，但不要夸大为普适标准。

**完成标准**：第 4 节读起来像方法论章节，而不是维护日志章节。

## C. 在不新增实验前提下的改稿原则

### C1. 明确采用“案例验证型系统论文”写法

- 主动承认当前稿件不是大规模 benchmark 论文。
- 将第 5 节从“Experiments and Results”弱化为“Case Study and Device-Side Validation”或“Device-Side Evaluation and Validation”。
- 保留现有训练曲线、验证批次预测图、五任务真机证据图和延迟统计，但重新解释其角色。
- 将 SafeHat 检测作为主案例定量验证来源，其余任务作为功能覆盖和解析正确性的系统验证证据。

**完成标准**：即使不新增实验，现有证据也能被解释为一套边界清晰的案例验证体系。

### C2. 不再追求“强 benchmark 叙事”

- 不声称方法在精度或速度上全面优于其他移动框架。
- 不暗示现有单设备延迟结果可以外推到所有 Android 平台。
- 不把一个设备上的 CPU 路径结果写成“系统实时性普遍结论”。
- 不用“五任务全面验证”这类容易引发追问的高强度表述，改为“五任务运行覆盖验证”。

**完成标准**：审稿人即使追问实验不足，也会认为作者已经主动控制了结论边界。

### C3. 最大化现有证据的呈现效率

- 保留图 8(a) 和图 8(b)，但明确它们服务于主案例模型可用性说明，而非整篇论文的中心。
- 保留图 8(c)，但将其表述为统一应用内五任务运行覆盖证据。
- 保留表 8 和表 9，并将它们前移或强化为“功能验证 + 故障修复成效”的核心表证。
- 保留表 10，但把它写成“设备端运行量级刻画”，而不是性能领先声明。
- 若不新增实验，可优先对现有日志和截图做更清晰图形化整理，而不是新增采样。

**完成标准**：现有图表之间形成“主案例训练质量 - 设备端功能验证 - 故障修复收益 - 运行量级刻画”的证据链。

### C4. 通过讨论和局限性降低审稿风险

- 在讨论中主动说明：当前结果主要建立在单设备、单主案例、单主要推理引擎路径之上。
- 明确本文未进行跨框架对比，也未进行跨设备泛化性评测。
- 说明本文价值在于给出统一部署与诊断工作流，而不是给出广泛性能最优结论。
- 对未来工作中的 GPU、量化、跨设备评测保留为后续方向，不要写成当前已部分完成。

**完成标准**：局限性写得越主动，越能减少审稿人把“未做的事”当成“应当已经做完的事”。

**完成标准**：结论收束为系统论文，而不是以算法论文口吻结束。
