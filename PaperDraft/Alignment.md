# Electronics 中文稿对齐方案

## 1. 目标

本文件用于约束当前中文技术稿在投稿前的三类一致性问题：

- 语法与学术表达风格检查
- 术语一致性与命名统一
- Markdown 结构约束与可维护性

本文件的所有规则以 §2 所定义的三贡献逻辑关系为基本逻辑原则，任何与该原则相违背的表述均需优先修正。

本轮对齐的目标不是直接生成最终期刊模板稿，而是先把当前 Markdown 主稿整理为一份风格稳定、术语统一、结构清晰、便于后续翻译和模板迁移的中间基线版本。

## 2. 基本逻辑原则

### 2.1 三贡献层级关系

本文的三条贡献具有明确的逻辑层级：

| 贡献 | 类型 | 说明 |
| --- | --- | --- |
| 贡献 1：统一部署架构 | **提出** | 独立方法贡献，不依赖 SafeHat 案例才能成立 |
| 贡献 2：五阶段诊断流程 | **提出** | 独立方法贡献，不依赖 SafeHat 案例才能成立 |
| 贡献 3：SafeHat 主案例 | **验证** | 通过具体实例对贡献 1 和贡献 2 进行端到端闭环验证 |

贡献 3 的逻辑地位是**验证**贡献 1 和贡献 2，而不是独立于前两者的第三类方法提出。

### 2.2 叙述顺序约束（方法优先原则）

全文任何位置的叙述均应遵循以下顺序：

> **先提出方法（贡献 1/2）→ 再以 SafeHat 案例验证（贡献 3）**

禁止将这一顺序倒置为：

> ~~先描述项目实现过程（SafeHat）→ 再总结出方法或框架~~

具体约束：

- 摘要、§1 引言、§6 结论中，均不得先出现 SafeHat 案例描述，再总结推出方法贡献
- 每个小节内部，如同时涉及方法提出和案例验证，应先陈述方法，再说明案例如何验证
- SafeHat 案例在正文中的作用是"提供验证场景"，不是"触发方法产生"的起点

### 2.3 动词选用约束

| 描述对象 | 正确动词 | 禁止用法 |
| --- | --- | --- |
| 贡献 1（部署架构） | 提出、设计、实现 | ~~构建了~~、~~总结自项目~~、~~由项目得出~~ |
| 贡献 2（诊断流程） | 提出、组织、给出 | ~~归纳自案例~~、~~实践中发现~~ |
| 贡献 3（SafeHat 案例） | 验证、给出（闭环验证）、以…为主案例 | ~~提出~~（案例本身不是方法） |
| 全文整体框架 | 提出 | ~~构建了~~ |

### 2.4 违禁叙述模式

以下模式违反 §2.1 层级关系，一经发现必须修正：

1. **倒置叙述**：先讲 SafeHat 项目做了什么，结尾总结"因此本文提出了方法 X"
2. **孤立验证**：描述 SafeHat 结果时不显式说明其验证了哪条贡献
3. **贡献混淆**：用"验证"描述贡献 1/2，或用"提出"描述贡献 3 的案例内容
4. **结论倒序**：§6 结论中 SafeHat 案例段落出现在方法贡献段落之前

### 2.5 避免"技术解释性"文章的检查准则

全文任意段落不得呈现"技术解释性文章"（即"系统如何工作"的说明文体）的特征。以下四条准则须逐节对照执行：

1. **方法主张优先**：每节的首要陈述是"本文提出什么方法、解决什么问题"，而不是"系统如何工作"或"算法步骤是什么"。
2. **技术细节嵌入方法叙述**：算法伪代码、公式推导、参数说明均须嵌入方法主张叙述中，作为支撑证据，而非独立成段的技术文档。
3. **可删性测试**：若某段删去后读者仍能理解方法主张，则该段可能是纯技术解释；须将其压缩或与方法动机合并。
4. **§3 小节首句约束**：§3 各小节不得以"系统由…组成"或"原始实现如何工作"作为首句；首句必须陈述本文贡献针对的问题及其解决方案。

### 2.6 整体科学路线（逐节检查锚点）

全文须贯穿"**提出方法 → 算法印证 → 实验回证**"的三段式科学路线，且绝不能读作"技术解释性文章"。各节的职责映射如下：

| 节 | 科学路线角色 | 核查要点 |
| --- | --- | --- |
| 摘要 | 三项贡献（C1/C2/C3）提出 → 部署架构与诊断流程形式化描述 → 实机测试数值 | 方法主张须在实机数值前出现；贡献 3 须以"验证"而非"提出"表述 |
| §1 引言 | 提出方法（C1/C2/C3），标准投稿格式 | 贡献 1/2 句以"提出"开头；贡献 3 以"给出闭环验证"表述；不描述实验结果 |
| §2 相关工作 | 铺垫研究空白，说明 C1/C2 的提出动机 | 不应出现新贡献声明；须与 §1 贡献背景显式对应 |
| §3（C1） | 方法主张先行（"针对…本文提出统一部署架构…"）→ 图 1 与架构各子系统印证 | 禁止以项目实现描述开头；§3.1 须先声明设计目标，再展开架构实现 |
| §4.1（C2 流程） | 方法主张先行（"本文进一步提出五阶段诊断流程…"）→ 五阶段步骤形式化印证 | 五步骤须与 §1 贡献 2 表述保持一致；步骤列出须完整 |
| §4.2–§4.5（C2 故障印证） | 四类故障逐一经由五阶段流程完成诊断 → 根因分析 → 修复 → 回归验证 | 每节须先陈述该故障与流程步骤的对应关系，再给出故障现象与修复结果 |
| §5.1（C3 SafeHat） | 实验回证：SafeHat 对 C1/C2 给出端到端闭环验证 | 须显式声明验证了哪条贡献；禁止对案例内容使用"提出"动词 |
| §5.2 | 实验回证：五任务覆盖验证对贡献 1 统一架构给出实机覆盖证明 | 须说明覆盖验证与贡献 1 统一调度声明的对应关系 |
| §5.3–§5.4 | 实验回证：实机延迟表征 + 适用范围与局限性边界声明 | 数据须为实测值；须给出局限性声明以防过度泛化 |
| §6 结论 | 统一收口：C1/C2 方法贡献 → 架构与诊断流程 → SafeHat 验证结果 → 局限性 → 未来工作 | 实验结果段落不得先于方法贡献段落出现 |

## 3. 适用范围

当前方案主要适用于以下文稿：

- Paper.md
- 论文框架.md
- 期刊论文.md
- 与论文撰写直接相关的说明性 Markdown 文件

默认不对以下内容施加严格写作约束：

- 日志文件
- 数据集说明原始文件
- 构建产物与自动导出结果
- 代码注释与实验脚本中的临时文本

## 4. 对齐原则

### 4.1 面向 Electronics 的稿件定位

当前中文稿应优先满足以下要求：

- 表述偏工程论文风格，而不是宣传性项目说明
- 贡献、方法、实验、结论四部分职责清晰，符合 §2.1 层级关系
- 贡献 1/2 以"提出"为核心动词，贡献 3 以"验证"为核心动词（详见 §2.3）
- 每个结论尽量对应具体实验、图表或误差现象
- 避免夸张判断、泛化结论和无证据强化语句
- 术语在全文保持单一首选写法，必要时允许首处全称加缩写

### 4.2 本轮不处理的内容

本轮不直接处理以下任务：

- 英文全文润色
- 参考文献格式重排
- 按期刊官方 Word 或 LaTeX 模板重排版
- 图表编号与交叉引用的最终模板映射

## 5. 基于当前中文稿的主要对齐点

结合当前主稿内容，优先收敛以下问题。

### 5.1 研究对象表述需要统一

以下说法目前存在混用，应收敛为固定表述：

- 资源受限 Android 设备
- 资源受限设备
- 低资源场景
- 低成本、广泛可得 Android 终端

建议：

- 论文本体对象统一优先使用“资源受限 Android 设备”
- 涉及部署条件或应用约束时使用“低资源场景”
- 涉及普及性和产业可获得性时使用“低成本、广泛可得的 Android 终端”
"资源受限 Android 设备"操作性定义（已在 §1 引言中明确，需与正文保持一致）：

> 使用通用移动 CPU 核心、不具备专用神经网络加速路径、在 fp32 精度下对 640×640 输入的推理吞吐量显著低于实时帧率阈值的在役移动终端，以低成本、广泛可得的中低端机型为典型代表。

三个可验证维度：

1. **算力结构**：通用 CPU 核心（ARM 大小核），NCNN 不启用 NPU 或专用加速器
2. **精度约束**：fp32，未量化
3. **吞吐量约束**：640×640 输入下推理吞吐量 < 实时帧率阈值（本文实测 2–3 FPS）

实验设备 HUAWEI P20 Pro（Kirin 970）满足上述三项，§5.3 表 10 延迟数据为实证依据。

使用约束：

- 首次引入"资源受限 Android 设备"时（§1）必须包含或紧跟操作性定义
- 后文不得仅凭设备品牌或型号声称满足"资源受限"条件，需与上述定义挂钩
- 选用 NCNN 的理由应突出轻量 C++ 运行时与成熟 ARM CPU 适配，而非将 Vulkan GPU 支持列为主要选型依据（Vulkan 路径在框架层面保留，但本文实验在 CPU 路径下完成）
### 5.2 设备侧表达需要统一

当前存在以下混用：

- 设备端
- 端侧
- 终端

建议：

- 涉及实现、推理流程、部署结果时统一优先使用“设备端”
- “端侧推理”可以保留在背景语境中，但不作为全篇默认主称
- “终端”仅在强调终端硬件形态时使用，不替代“设备端”

### 5.3 模型导出与后处理相关术语需要统一

当前已有或潜在混用包括：

- param-bin / param bin / param/bin
- Top-K / top-k
- One-to-Many / O2M

建议：

- 文件对统一写为“param/bin 文件对”
- 候选筛选统一写为“Top-K”
- 第一次出现写为“One-to-Many（O2M）”，后文可根据上下文使用 O2M

### 5.4 模板化学术表述需要压缩

当前稿件中已发现若干容易带有模板感的表达，应优先清理：

- 进一步地
- 总体而言
- 需要指出的是
- 这正是
- 具有重要意义
- 显著改善
- 可复用的系统化方法
- 更具可操作性的系统方法

替换原则：

- 用具体对象、条件、范围、实验现象替代抽象评价
- 用“在什么设备、什么任务、什么指标上得到什么结果”替代泛化判断
- 用“本文观察到”或“实验结果表明”替代无主体的结论句
### 5.5 元陈述表述需要清除

正式研究文章的正文不应出现向读者解释写作策略或稿件类型的句子（"元陈述"）。这类句子的特征是作者在谈论这篇论文是什么，而不是在陈述研究本身做了什么。

当前已发现或潜在出现的典型形式：

- 本文的投稿定位是……
- 本文应被理解为……
- 本文整体定位为……系统研究
- 说明本文的系统论文定位
- 本文不应被视为……而应被视为……

替换原则：

- 将"本文的投稿定位是 X"改为"本文聚焦于 X"或"本文研究 X"
- 将"本文应被理解为 X 的提出与验证"改为"本文提出并验证了 X"
- 将"说明本文的系统论文定位"改为"说明本文的研究范围与现有工作的差异"
- 凡描述论文类型归属的句子，均替换为对研究内容、范围或边界的直接陈述

### 5.6 贡献叙述顺序与动词约束（派生自 §2）

本节是 §2 在具体稿件检查中的落地规则，适用于 Paper.md 所有章节。

**顺序检查清单**（每次修改摘要、§1、§6 后必检）：

1. 摘要中是否先出现方法描述（贡献 1/2），再出现验证描述（贡献 3）？
2. §1 引言贡献列表是否按 贡献1 → 贡献2 → 贡献3 顺序排列？
3. §6 结论是否在 SafeHat 案例段落之前出现部署架构和诊断流程段落？
4. §4.2–4.5 每个故障模式小节是否先陈述诊断流程步骤，再给出 SafeHat 实例结果？

**动词检查清单**：

- 贡献 1/2 前是否使用"提出"（而非"构建了"、"归纳了"、"基于项目得到"）？
- 贡献 3 描述是否使用"验证"/"给出闭环验证"（而非"提出"）？
- 结论中是否出现"通过 SafeHat 案例对上述方法进行了验证"或等效表述？

## 6. 工具栈与职责分工

### 6.1 markdownlint

用途：

- 约束标题层级
- 约束列表与空行
- 约束围栏代码块写法
- 保持 Markdown 结构稳定、可维护

不承担的职责：

- 不负责中文语法判断
- 不负责术语统一
- 不负责学术风格判断

### 6.2 cspell

用途：

- 管理英文技术名词拼写
- 固定缩写、模型名、文件名、框架名写法
- 降低英文大小写和连字符不一致的问题

重点覆盖对象：

- NCNN
- YOLO26
- SafeHat
- Vulkan
- OpenCV
- Ultralytics
- OBB
- PPE
- Top-K

### 6.3 Vale

用途：

- 检查中文学术表达是否过于模板化
- 检查术语替换和首选写法
- 对宣传式或证据不足的判断句给出提示

Vale 是本方案的主检查器，用于承接“语法风格检查 + 术语一致性”的核心任务。

## 7. 术语一致性规则

### 7.1 首选术语表

| 类型 | 首选写法 | 备注 |
| --- | --- | --- |
| 研究对象 | 资源受限 Android 设备 | 全文默认主称 |
| 约束环境 | 低资源场景 | 用于部署条件与算力约束 |
| 部署位置 | 设备端 | 用于实现、推理、验证 |
| 文件对 | param/bin 文件对 | 不再混写 |
| 候选筛选 | Top-K | 英文大小写固定 |
| 训练分配策略 | One-to-Many（O2M） | 首次全称加缩写 |
| 推理引擎 | NCNN | 大写固定 |
| 案例数据集 | SafeHat | 大小写固定 |
| 贡献 1/2 核心动词 | 提出 | 不用"构建了"或"归纳了" |
| 贡献 3 核心动词 | 验证 / 给出闭环验证 | 不用"提出" |

### 7.2 使用规则

- 一个概念只保留一个默认主称
- 第一次出现的英文机制或策略采用“中文说明 + 英文全称或英文术语”的方式
- 同一节内部不交替切换同义写法
- 图题、表题、正文、结论中的术语保持一致
- 文件名、模型名、脚本名允许保留其真实拼写，不强制改写成正文术语
- 贡献 1/2 对应的方法段落不得将 SafeHat 作为方法成立的前提条件

## 8. 语法与风格检查规则

### 8.1 句子层面

- 单句优先表达一个核心判断
- 避免连续多层定语导致的长句堆叠
- 结论句尽量带有条件、对象或证据来源
- 避免无主语的泛化评价句

### 8.2 学术风格层面

- 少用“重要意义”“显著提升”“更具可操作性”这类抽象强化词
- 如需使用“显著”，应有明确指标、对比组或误差范围支撑
- 少用“总体而言”“进一步地”作为机械段落连接
- 将“这正是”替换为更具体的因果或问题定义句
- 正文中不出现元陈述：不解释本文属于哪种稿件类型，只陈述本文研究了什么（详见 §5.5）
- 叙述顺序须符合 §2.2 方法优先原则，不得以项目实现倒推方法贡献

### 8.3 建议替换范式

建议将下列表达：

- 具有重要意义
- 显著改善
- 可复用的系统化方法

替换为以下范式之一：

- 在某设备与某任务上验证了某方法的可行性
- 相比某基线，某指标提升或波动控制在某范围内
- 本文给出了从导出、部署到一致性诊断的完整实现路径

## 9. Markdown 结构约束

### 9.1 标题层级

- 文档只保留一个一级标题
- 正文主体使用二级标题承载章节
- 三级标题用于章节内分点，不继续向下细分，除非确有必要

### 9.2 段落与列表

- 标题上下保留空行
- 列表前后保留空行
- 列表项尽量保持平行结构
- 连续短句不要机械拆成过多列表

### 9.3 图表与代码块

- 图题和表题保持统一格式
- 围栏代码块统一使用反引号
- 代码块尽量带语言标记；流程或伪输出可使用 text
- 数学公式继续使用独立块级公式，不嵌入列表项内部造成阅读断裂

### 9.4 不强制的结构项

为了避免对中文技术稿产生过多噪声，以下约束本轮不强制：

- 每行长度上限
- 参考文献中的裸链接
- 图表说明行的强调写法

## 10. 自动检查落地方式

本轮落地采用以下分工：

- .markdownlint.jsonc：负责 Markdown 结构边界
- cspell.json：负责英文术语、缩写与拼写白名单
