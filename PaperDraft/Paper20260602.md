## Abstract
As global power resources become increasingly constrained, edge computing is expected to absorb a growing share of computational demand, making custom YOLO26 deployment on resource-constrained Android devices increasingly significant. This article presents a reproducible Android-NCNN deployment and diagnosis method for YOLO26, using a SafeHat 10-class personal protective equipment task as the demonstration case. The workflow covers fine-tuning, PyTorch-to-ONNX/NCNN conversion, Android asset replacement, Java-JNI-C++-NCNN inference integration, on-device threshold and display-score configuration, and CPU-path validation on low-end Android phones. It defines five diagnostic stages for silent deployment errors: anomaly logging, intermediate-output inspection, cross-backend comparison, graph-structure tracing, and frozen-image regression. The workflow is exercised across detection, segmentation, pose estimation, classification, and oriented bounding-box assets. Four representative faults validate the method. Repairing a letterbox mismatch reduced empty-scene median scores from 0.84-0.96 to below 0.0001. Removing a redundant sigmoid restored scene-dependent probabilities with $p_{50} \approx 0.34$ and $p_{95} \approx 0.74$. Coordinate-semantic and OBB-layout repairs restored pose, oriented-box geometry, class labels, and angles. A 48-image frozen sweep and two Android CPU phones show that the method localizes deployment inconsistencies and provides a reusable Android-side visual model migration template.
**Keywords:** Android deployment; NCNN; YOLO; deployment consistency; model conversion; JNI; PPE monitoring; reproducible workflow; edge inference
## 1. Introduction
Mobile and embedded visual inference increasingly relies on model conversion rather than training directly in the final runtime. A common path is to fine-tune a YOLO-family model with Ultralytics YOLO and export it through ONNX or an engine-specific converter [1,2]. On Android, the exported model can be executed through mobile inference runtimes such as NCNN or TensorFlow Lite [3,4]. Other deployment choices, including ONNX Runtime Mobile and MNN, are also used when application constraints or runtime support differ [5,6]. The same conversion pattern is used for detection models whose output semantics have evolved from early YOLO-style dense predictions to newer end-to-end detection structures [7,8]. Contemporary YOLO variants further illustrate the pace of real-time detector architecture change [9,10]. Transformer-based real-time detector comparisons also show that output semantics continue to diversify [11]. Segmentation and oriented bounding-box tasks add mask, angle, or geometry-specific outputs that require task-aware parsing [12,13]. Recent Android object-detection applications further show the practical demand for deploying YOLO-family models on mobile devices [14,15]. Android integration itself introduces native interfaces, camera preprocessing, and runtime configuration through components such as NDK/JNI and CameraX [16,17]. This local execution path is attractive, but it also creates a consistency problem: the model that appears correct in the desktop environment may not be semantically identical after export, parser adaptation, JNI integration, camera preprocessing, and on-device post-processing.
The most damaging deployment errors do not always appear as model-loading failures. They often appear as high-confidence detections on empty backgrounds, confidence values fixed around 0.5, missing skeletons, shifted oriented boxes, or labels that are systematically wrong while the application keeps running. These symptoms are difficult to interpret from a single screenshot or a single final output because the root cause may come from any point in the chain: input resizing, padding, normalization, ONNX-to-NCNN conversion, an inserted activation in the exported graph, C++ tensor traversal, a task-specific parser, or the UI display transformation.
This article focuses on that deployment-consistency problem as a method problem. The target setting is a resource-constrained Android device: an in-service mobile device that runs the NCNN CPU path on general-purpose ARM cores, without using a dedicated neural accelerator, quantization, or GPU/Vulkan acceleration in the reported measurements. The study uses the project-managed `yolo26n` asset set and a SafeHat PPE deployment as the demonstration case, but the method is not tied to PPE monitoring. Its reusable object is the diagnosis workflow for YOLO-to-NCNN Android inference.
The contributions are as follows:
1. A reproducible YOLO26-to-Android-NCNN deployment protocol is provided, covering model fine-tuning, PyTorch-to-ONNX/NCNN conversion, Android asset replacement, Java-JNI-C++ integration, threshold and display-score configuration, and on-device logging.
2. A five-stage diagnosis workflow is defined for silent Android deployment inconsistencies, including anomaly logging, intermediate-output inspection, cross-backend comparison, graph-structure tracing, and frozen-image regression. The workflow localizes preprocessing mismatch, redundant activation, coordinate semantic errors, and output-layout interpretation errors.
3. A reusable validation package is demonstrated across detection, segmentation, pose estimation, classification, and oriented bounding-box assets, using 48 frozen images and two low-end Android CPU devices to document regression behavior, task transferability, and runtime feasibility.
## 2. Method Overview
### 2.1 Problem definition
The workflow diagnoses deployment inconsistency between a desktop-side YOLO model and an Android-side NCNN application. The method assumes that the user has a trained or fine-tuned YOLO-family model, an NCNN export path, an Android application that loads NCNN param/bin files, and at least one reference input that can be run in more than one backend.
The workflow treats the Android inference path as a sequence of observable transformations:
```text
training model -> exported graph -> NCNN param/bin -> Android asset ->
JNI/native inference -> task parser -> post-processing -> rendered output/log
```
The method receives raw symptoms from the Android application and produces four outputs: a fault category, the suspected root cause, a repair action, and a regression artifact that verifies the repair.

### 2.3 Five-stage diagnosis logic
The method is organized as five stages. The stages need not always be executed to completion; they act as decision gates. For example, if cross-backend comparison directly isolates a preprocessing fault, graph tracing may not be needed for that fault. Regression validation remains mandatory after any repair.
**Figure 2.** Five-stage fault diagnosis workflow for Android deployment.  
![Figure 2 - fault diagnosis workflow for Android deployment](runs/paper_figures/Figure_4.svg)
**Table 2. Five-stage diagnosis workflow.**
| Stage | Name | Input | Operation | Exit criterion | Project tools |
|---|---|---|---|---|---|
| S1 | Anomaly logging | Android logs, screenshots, rendered output | Record abnormal scores, fixed confidence values, missing geometry, label disorder, or loading errors | The symptom is reproducible and numerically described | `logcat`, `diagnose_background_scores.py`, `collect_latency.py` |
| S2 | Intermediate-output inspection | NCNN param/bin, tensor shapes, parser assumptions | Inspect output names, output widths/heights, class count, and tensor value ranges | The deviation is localized to a tensor shape, numerical range, or parser expectation | `verify_ncnn_output.py`, `diagnose_model.py` |
| S3 | Cross-backend comparison | Same image in PyTorch, ONNX, Python-NCNN, Android-NCNN | Compare output distributions and rendered behavior across backends | The fault is assigned to export/conversion or Android-side implementation | `trace_conversion_pipeline.py`, `diagnose_model.py` |
| S4 | Graph-structure tracing | NCNN param graph and native parser code | Trace Sigmoid nodes, concat chains, output-column order, and coordinate semantics | The root branch, operator, or column assumption is identified | `conversion_detail_check.py`, parser inspection |
| S5 | Regression validation | Repaired app and frozen scenes | Re-run affected scenes and previously passing scenes | The abnormal diagnostic signal is removed and no known passing case regresses | `test_letterbox_hypothesis.py`, `test_yolo26_e2e.py`, `sensitivity_sweep.py` |

### 3.1 Software assets and environment
The implementation uses a Java-JNI-C++-NCNN Android application. The method requires direct control over preprocessing, parser code, and logging because many deployment faults are introduced after the exported model is already valid. The demonstration combines NCNN for mobile inference [3], OpenCV-Mobile for image operations [18], Android NDK/JNI components [16], and the retained Vulkan-capable NCNN package even though the reported measurements use the CPU path [19].

The demonstration model uses a SafeHat dataset definition with 10 classes: Hardhat, Mask, No-Hardhat, No-Mask, No-Safety Vest, Person, Safety Cone, Safety Vest, Machinery, and Vehicle. The local project contains 2685 training images and 114 validation images under `data/train` and `data/valid`, and the frozen method-validation sweep uses 48 images under `data/testdata`. The training-stage model reached precision 0.857, recall 0.723, mAP50 0.796, and mAP50-95 0.496 at the last recorded epoch of `runs/detect/runs/calib/safehat_confcal_v3/results.csv`. These values are used only to confirm that the demonstration model is usable before deployment diagnosis.
### 3.2 YOLO-to-NCNN export and asset deployment protocol
The protocol converts a trained model into Android assets and checks whether the output tensors still match the native parser. The project uses Ultralytics export utilities [1], ONNX-related conversion checks where needed [2], and PNNX/NCNN inspection tools as auxiliary conversion references [20]. Table 4 lists the reproducible steps.
**Table 4. Export and Android asset deployment protocol.**
| Step | Input | Operation | Expected artifact | Failure signal |
|---|---|---|---|---|
| P1 | `safehat.yaml`, training images, pretrained `yolo26n.pt` | Fine-tune or load a trained YOLO model | `best.pt`, validation curves, class list | Missing class names or unstable validation output |
| P2 | `best.pt` | Export to NCNN through Ultralytics or conversion scripts | param/bin file pair | Export failure, unsupported operator, missing output |
| P3 | NCNN param/bin | Inspect layer graph and output dimensions | Output-shape report | Unexpected width/height, missing `out0`, class-count mismatch |
| P4 | Android asset directory | Copy or replace assets under `app/src/main/assets/` | Android-loadable model files | `loadModel` failure or JNI resource-path error |
| P5 | Android app and reference scenes | Run on-device logging and visual regression | logcat lines, screenshots, diagnostic tables | High background score, fixed confidence, missing geometry, label disorder |
The detection demonstration uses `yolo26n_safehat.ncnn.param/bin` as the preferred semantic asset name. A historical compatible alias, `yolo26n_e2e`, is also present in the project. In the SafeHat main case, the detection output is treated as an O2M tensor with 8400 proposals and 10 classes rather than as a fully decoded E2E `300 x 6` tensor. The workflow explicitly records this distinction because a name-level alias can otherwise mislead the native parser.
### 3.3 Android-NCNN inference and logging path
The Android application is divided into four layers: Java interaction, JNI bridge, native C++ inference and parsing, and the low-level NCNN/OpenCV/NDK dependency layer. The Java layer handles task selection, threshold updates, and display. The JNI bridge transfers task IDs, thresholds, and native object lifecycles. The C++ layer loads the corresponding NCNN model, preprocesses camera frames, executes inference, parses the task-specific output, applies post-processing, and emits logcat records.

### 3.4 Preprocessing and post-processing rules
The workflow treats preprocessing as a first-class consistency check. For the four 640 x 640 vision tasks, the Android path uses letterbox resizing with padding value 114. Let the original width and height be $W$ and $H$, and let the target side length be $S$. The scale factor and resized size are
$$
r = \min(S/W, S/H), \quad W' = \lfloor rW \rfloor, \quad H' = \lfloor rH \rfloor.
$$
The padding values are
$$
p_x = \left\lfloor (S - W')/2 \right\rfloor, \quad
p_y = \left\lfloor (S - H')/2 \right\rfloor.
$$
When a box is mapped back to the original image,
$$
x = (\hat{x} - p_x)/r, \quad y = (\hat{y} - p_y)/r, \quad
w = \hat{w}/r, \quad h = \hat{h}/r.
$$
The repair rule is to pad the input to a strict `target_size x target_size` tensor, not merely to a stride-aligned rectangle. The latter can produce a 640 x 384 tensor for a 1920 x 1080 input and changes the input distribution seen by the model.
For the SafeHat detection demonstration, the device reports a diagnostic display score
$$
\tilde{p}_{dev} = \sigma \left( \frac{\log(p/(1-p))}{T_{dev}} \right), \quad T_{dev}=3,
$$
where $p$ is the raw model probability and $\sigma$ is the sigmoid function. This transformation is used for diagnostic display and threshold readability; it is not presented as a detector-accuracy improvement. The offline parameter sweep uses a two-stage display-compression variant
$$
\tilde{p}_{T,\gamma} =
\left[ \sigma \left( \frac{\log(p/(1-p))}{T} \right) \right]^\gamma .
$$
The SafeHat post-processing path also includes per-class Top-K candidate retention, per-class NMS, mutually exclusive suppression for conflicting class pairs such as Hardhat and No-Hardhat, person-dependent PPE association, and PPE box locking. These mechanisms are kept in the method description because they create observable diagnostic signals during regression, but their parameter sweep is interpreted as a protocol demonstration rather than as a universal parameter recommendation.
### 3.5 Fault-specific repair templates
The workflow converts fault cases into reusable templates. Table 6 lists the four templates validated in the project.
**Table 6. Reusable fault diagnosis and repair templates.**
| Fault mode | Symptom | Diagnostic signature | Root-cause check | Repair rule | Regression criterion |
|---|---|---|---|---|---|
| Preprocessing mismatch | Empty scenes produce many high-confidence detections | Background score median and high-score fraction are abnormal | Compare desktop inference with Android tensor size and padding | Emit a strict 640 x 640 letterbox tensor with padding value 114 | Empty-scene score distribution returns to near zero and target-present scenes still detect Person/PPE |
| Redundant activation | Confidence values collapse near 0.5; dense pseudo-candidates appear | Backend output already lies in probability range and parser applies sigmoid again | Trace Sigmoid nodes in NCNN graph and parser activation code | Remove duplicate sigmoid in parser while retaining required task-specific transforms | Confidence distribution becomes scene-dependent rather than fixed near 0.5 |
| Coordinate semantic mismatch | Pose skeleton or OBB geometry disappears or leaves image bounds | Output coordinates have already-decoded pixel scale, but parser applies grid/stride decoding | Inspect output magnitudes and E2E export path | Add parser branch for already-decoded E2E outputs | Keypoints and oriented boxes render in frame coordinates |
| OBB layout mismatch | Labels and directions are systematically wrong | Parser assumes `[bbox, angle, classes]`; graph stores `[bbox, classes_sigmoided, angle_raw]` | Trace concat chain and output columns | Move class start and angle column handling to the actual layout | OBB class labels, confidence values, and directions are interpretable |

### 4.2 Validation on four representative fault modes
The four fault modes validate whether the workflow can move from an observed symptom to a repair and a regression artifact. Table 8 summarizes the evidence.
**Table 8. Fault symptoms, diagnosis path, and repair evidence.**
| No. | Fault type | Workflow stages used | Observed symptom | Root cause | Repair evidence |
|---|---|---|---|---|---|
| 1 | Preprocessing mismatch | S1, S2, S3, S5 | Empty scenes triggered all 10 classes; `p50 = 0.84-0.96`, `frac_gt090 = 0.41-0.58` | Android preprocessing padded to a stride-aligned 640 x 384 tensor instead of a strict 640 x 640 tensor | After repair, `p50 < 0.0001`, `p99 = 0.0006-0.0029`, `frac_gt090 < 0.000001`, and false detections disappeared |
| 2 | Redundant activation | S1, S3, S4, S5 | Confidences were fixed near 50%; changing threshold did not separate background and objects | NCNN graph already contained sigmoid, while C++ parser applied sigmoid again | Raw probabilities recovered to a scene-dependent distribution with $p_{50} \approx 0.34$, $p_{95} \approx 0.74$, and upper bound near 0.95 |
| 3 | Coordinate semantic mismatch | S1, S2, S4, S5 | Pose skeleton missing; OBB geometry absent or outside view | E2E output coordinates were already decoded, but parser applied legacy grid/stride restoration | Pose keypoints and OBB geometry rendered normally after adding an E2E parser branch |
| 4 | OBB layout mismatch | S1, S3, S4, S5 | OBB labels, confidences, and directions were abnormal | Parser assumed `[bbox, angle, classes]`, while actual output stored `[bbox, classes_sigmoided, angle_raw]` | Corrected column indices restored class labels, confidence values, and orientation display |
The preprocessing repair is the clearest numerical validation. In the faulty state, a non-square camera input could be resized and padded only to a stride-aligned shape. For a 1920 x 1080 frame, this produced a 640 x 384 input rather than the expected square tensor. Cross-backend comparison showed that the desktop model and Python-side reference behaved normally, while the Android path received a different tensor shape. Repairing the native preprocessing to emit a strict 640 x 640 letterbox tensor removed the empty-scene high-score signature.
**Figure 6.** Input-pattern and detection comparison before and after the preprocessing repair.  
![Figure 6 - preprocessing fix comparison](runs/paper_figures/Figure_5.svg)
The redundant-activation fault validates S4 graph-structure tracing. Structure inspection identified Sigmoid nodes already present in the exported NCNN graph. The C++ parser then applied another sigmoid to class-related outputs, mapping low background scores toward 0.5 and producing dense pseudo-candidates. Removing the duplicate activation restored a probability distribution that changed with scene content.
**Figure 7.** Effect of single versus repeated sigmoid application.  
![Figure 7 - single versus repeated sigmoid effect](runs/paper_figures/Figure_6.svg)
The coordinate and OBB faults validate parser-semantic tracing. E2E branches may output already-decoded pixel coordinates, while a legacy parser expects grid-relative values and applies stride restoration. The repair adds a branch that uses decoded E2E outputs directly. For OBB, tracing the concat chain showed that the parser read a class probability as an angle and shifted subsequent class indices; correcting the column layout repaired both class and direction rendering.

For a new deployment, the minimal regression checklist is:
1. Confirm that the Android app loads the expected param/bin file pair.
2. Confirm that task-specific output shape and class count match the parser.
3. Run an empty-background input and record background score quantiles.
4. Run at least one target-present input and confirm a plausible raw-score range.
5. Compare the same input between desktop reference and Android-side NCNN if a symptom appears.
6. Inspect graph-level activations and output-column layout when value-range comparison is insufficient.
7. Re-run the previously failing input and at least one previously passing input after repair.
### 4.4 Parameter sensitivity demonstration
The frozen sweep does not establish universal parameter values. It demonstrates how the method records the effect of post-processing settings on a fixed validation set after the raw model output is cached once. The script `scripts/sensitivity_sweep.py` evaluates 48 images: 18 target-present, 15 empty-background, and 15 hard-negative. The raw output is reused across all settings, so changes in the metrics come from the post-processing parameters.
The metrics are defined as follows: `FP_empty` is the mean number of final boxes on empty-background images; `frac_gt090` is the fraction of final boxes whose offline display score is above 0.90; `TP_keep` is the fraction of target-present images retaining at least one Person or PPE-class detection; `Mean cand.` is the mean pre-NMS candidate count after per-class Top-K; and `UI range` is the offline display-score range on target-present images.

The sweep confirms that $T$ and $\gamma$ mainly affect display-score readability, while $K_c$ and NMS overlap affect candidate retention and empty-scene box counts. The table should therefore be read as a reproducibility artifact for the diagnosis protocol, not as a detector-performance ablation.

## 5. Method Characteristics and Limitations
The workflow is reusable because its decision points are not specific to SafeHat PPE monitoring. Letterbox mismatch, redundant activation, decoded-coordinate misinterpretation, and output-layout mismatch can occur in many YOLO-to-NCNN Android deployments. The method also keeps the evidence chain explicit: every repair is tied to a diagnostic signal and a regression criterion rather than to visual inspection alone.
The method has several boundaries. First, the most complete quantitative validation is concentrated in the SafeHat detection case. The segmentation, pose, classification, and OBB assets are used to exercise heterogeneous output formats and runtime switching, but they are not evaluated with full task-level benchmarks. Second, the 48-image sweep is a frozen protocol demonstration and not a replacement for a large detection test set. Third, the reported latency values come from two Android phones on the NCNN CPU fp32 path; they do not compare NCNN with TensorFlow Lite, MNN, or ONNX Runtime Mobile under matched quantization and preprocessing. Fourth, the workflow assumes that at least one desktop-side or Python-side reference can be executed. If no cross-backend reference is available, S2 tensor inspection and S4 graph tracing carry more of the diagnosis burden.
These limitations do not invalidate the method goal. The validation demonstrates that the workflow can expose and repair representative deployment inconsistencies with project-level scripts, logs, frozen images, and Android assets. A future extension can add automated CI-style export checks, larger frozen-scene pools, matched cross-runtime comparisons, and INT8 or GPU/Vulkan variants.
## 6. Conclusions
This article reconstructed the Android-NCNN PPE deployment work as a reproducible YOLO26-to-Android-NCNN deployment and diagnosis method. The method links model preparation, NCNN conversion, Android asset replacement, Java-JNI-C++ inference integration, on-device logging, and regression validation into a practical protocol that can be executed with project scripts and Android log artifacts.
The SafeHat demonstration validated the workflow on four deployment fault modes. A preprocessing mismatch was localized to stride-aligned padding and repaired by enforcing a strict 640 x 640 letterbox tensor; the empty-scene median score dropped from 0.84-0.96 to below 0.0001. A redundant activation fault was localized by graph and parser tracing, after which raw probabilities recovered from a near-0.5 collapse to a scene-dependent range. Coordinate semantic repair restored pose and OBB geometry, and OBB output-layout tracing corrected class and angle interpretation. The 48-image sweep and two-device latency logs further show that the method can record post-processing and runtime evidence without converting the paper into a detector benchmark.
The resulting MethodsX contribution is threefold: a reproducible deployment protocol, a five-stage diagnosis workflow, and a reusable validation package for Android-NCNN deployment of YOLO-based visual inference models.
